# Работа с репозиторием данных MojiLex

## Границы и источники правил

- Здесь находятся канонические текстовые данные, схемы и инструменты их проверки.
  Импорт Telegram, анализ AI, интерактивное меню и отправка данных принадлежат
  отдельному репозиторию `mojilex-cli`; не добавляй их сюда.
- Перед изменениями прочитай `CONTRIBUTING.md`, `FORMAT.md` и относящуюся к задаче
  часть `docs/maintenance.md` (есть `docs/maintenance_RU.md`).
- Проверяй `git status`, текущий commit и отличия от целевой ветки. Локальная
  `main`, `origin/main` и ветка открытого PR могут различаться. Сохраняй чужие
  незакоммиченные изменения; для другой основы используй отдельный worktree.
- Проверка и аудит по умолчанию read-only. Push, merge, выпуск, удаление данных
  и внешние изменения выполняй только в явно согласованном объёме.

## Устройство и инварианты

- `dataset.json` задаёт корневой контракт; `data/` содержит коллекции, эмодзи,
  memberships и подтверждённые визуальные связи; `tombstones/` — записи удаления.
- `schemas/v1/` задаёт канонические записи, `schemas/distribution/v1/` — снимки
  и transport-контракты. Реестры находятся в `analysis-profiles/`, `taxonomy/`,
  `platforms/`, `rights/` и `quality/`. `examples/` — тестовые примеры, не база.
- Сохраняй namespace и детерминированные идентификаторы. Не объединяй разные
  native identities из-за одинаковых fingerprints и не меняй пути без необходимости.
  Проверяй текущие правила новых и поддерживаемых legacy bucket-путей в `FORMAT.md`.
- Для канонического JSON/JSONL используй порядок и сериализацию `tools/common.py`:
  UTF-8 без BOM, LF, установленный порядок ключей и сортировка записей.
  Authority-файлы могут требовать точные JCS-байты без завершающего LF.
- Обязательны согласованные описания `ru` и `en`. Статичные media требуют
  `not_applicable`; анимированные не допускают этот статус. Неизвестное движение
  обозначай `undetermined` с `motion` в `facets.uncertainties`, без выдуманного движения.
- Контролируемые категории и стили храни в `facets`, не дублируй их в
  `semantic_tags`. `fragment` допустим только для подтверждённой части композиции.
- Сохраняй настоящее происхождение, content labels и review status. Семантическая,
  media- или provenance-правка сбрасывает существующее одобрение в `unreviewed`.
  Не приписывай AI-правке человеческую проверку; не обновляй `last_verified_at`
  без проверки источника или документированного решения проверяющего.
- Не добавляй исходные media, кадры, архивы, ключи, временные URL, персональные
  данные или runtime-кеши. Обычная недоступность не является основанием удаления.

## Проверки

Команды выполняются из корня. Нужен Python 3.11+; используй существующий `.venv`.
На Windows вызывай интерпретатор явно, если `python` указывает на WindowsApps.

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe tools/validate.py . --strict
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -m ruff check tools tests
.\.venv\Scripts\python.exe -m ruff format --check tools tests
git diff --check
```

На Linux/macOS эквивалентный интерпретатор — `.venv/bin/python`.
Если среды нет, создай её через доступный Python: `python -m venv .venv`.
Для небольших правок выбирай соразмерные проверки; изменение схем и семантики
проверяй тестами, включая граничные случаи. Валидаторы работают офлайн.

- Изменение схемы требует проверки примеров, нормативных векторов и
  `tests/test_conformance_distribution_v1.py`: встроенные resource hashes меняются.
  Не обновляй ожидаемые хеши только ради прохождения теста без проверки причины.
- Снимок собирает `tools/build_index.py`; его проверяет `tools/validate_distribution.py`.
  Используй команды из maintenance guide с явными revision, snapshot ID и epoch.
  Source tree должен соответствовать выбранному commit. Не коммить `work/` и `dist/`.
- Проверка воспроизводимости означает две сборки с одинаковыми входами и сравнение
  всех байтов; успешная сборка один раз этого не доказывает. Не отключай проверки
  для зелёного CI. Точные текущие задания смотри в `.github/workflows/`.
- Локальный снимок и CI artifact не равны официальному релизу; правила публикации
  описаны в `docs/RELEASE_STAGING.md`. В отчёте различай локальные проверки, CI,
  push, merge и публикацию и указывай проверенный commit.
